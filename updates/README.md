# Release updates

Both apps check only when the user chooses Check for updates. Published downloads
are described by feed.json, authenticated by a detached ECDSA P-256/SHA-256 DER
signature. The public key is compiled into both clients. The private key is kept
outside git and in the private PFLOW_UPDATE_SIGNING_KEY repository secret.
Never publish that private key. Keep a private backup; existing clients cannot
accept a replacement key without a bridge release or a manual install.

After a GitHub release is published, publish-updates.yml reads GitHub's asset
SHA-256 digests, validates names and sizes, signs the feed, and commits both feed
files atomically. Older releases cannot lower a platform's published version.
A changed binary must have a new version. Source commits alone do not produce
installable updates: publish the tested binary release.

Windows release assets must include pFlow-Windows-{x64,x86,arm64}-VERSION-update.zip,
generated by scripts/package-update-zips.py from the tested payload directories.
They omit the existing speech/text model weights. The model pin must remain
compatible; a model change needs a full installer and an updater migration.
Mac assets use pFlow-Mac-VERSION-testing.dmg. Keep the full universal Windows ZIP
and Mac DMG available for a first install or recovery. Both apps retain the
previous application folder when replacing it; user data remains outside the app.

The update protocol allows only HTTPS downloads from this GitHub repository and
GitHub's release CDN. Clients verify the feed signature, platform, version,
expected byte count and SHA-256 before installation. Windows also rejects unsafe
ZIP paths, links, extra files, and file hash mismatches. No new program runs until
these checks pass and the user chooses Install and restart.
